00 Audience frame

Building an
agent harness.

The hard part is not one more tool call. It is the harness around the model: intake, background work, long-lived state, extension points, context assembly, and a path for the agent to improve its own tools.

  • React to software systems: tests, CI, review, issue trackers, logs, peers.
  • Keep state outside the prompt: queues, handles, snapshots, typed objects — then render only the useful projection.
  • Let capabilities become code: plugins the agent can read, edit, test, reload, and expose as context.
  • Interleave agentic loops and orchestration: let Python own the outer control flow while generation methods handle judgment, synthesis, and code acting.

01 Refresh

What are
NeMo OO Agents?

NeMo OO Agents is a Python harness where an agent is an object, generation methods are methods, tools are attributes, events become rendered context, and skills are editable libraries. The model sees source-shaped APIs and rendered runtime state in the same prompt.

01Typed methodsSignatures and Pydantic models are the task contract: typed inputs, typed outputs, validation, and docs.
02Pass by referenceArguments are live Python values — dataframes, meshes, handles — not stringified prompt blobs.
03Code as actionCodeAct emits Python; the REPL executes it; outputs become events the next turn can reason over.
04Loop engineeringPlain Python orchestration composes with generation methods: for, if, asyncio.gather.
05Object stateLong-lived state lives on self, managers, handles, snapshots — not only in the context window.
06Context blocksStatic, events, and dynamic blocks rebuild the model's world every turn with cache-friendly ordering.

04 Async behavior

Async without a
special agent DSL.

A queue-mode channel buffers values and can be drained by the dispatcher or by agent code mid-turn. An event-mode channel writes into the event log and wakes the dispatcher. spawn() runs coroutines or async generators in the background and routes outputs to a channel.

  • Backpressure point: every item has a name and a consumer.
  • Visibility: queue status is a dynamic context block.
  • Control: handles expose state, buffered values, and cancellation.
ch = self.queue_manager.queue("ci")

h = self.queue_manager.spawn(
    self.producers.monitor("make test"),
    channel="ci",
    buffer=100,
    label="pytest monitor",
)

05 API shape

The API is deliberately
mid-distribution Python.

The model should not have to learn your bespoke graph runtime, YAML orchestration language, or new effect system. It already knows objects, methods, docstrings, async, queues, files, tests, and context managers.

less fluent invent a new planning DSL, then teach the model the semantics and all the edge cases.
nemo-oo expose a Python object with real managers: self.todo, self.shell, self.queue_manager, self.context, self.skills.
payoff framework extensions are just Python too — a skill can add queues, context blocks, slash commands, types, subagents, and lifecycle hooks.

Skills

Plugins the agent
can edit.

A skill is not a prompt snippet. It is a Python library with lifecycle, dependencies, commands, context, tests, and source the agent can edit.

06 Skill registry

Discover, load,
activate.

The registry separates “available on disk” from “attached to the object” from “visible to the model.” That means tools can exist, be hidden, become visible, and disappear without restarting the session.

discoverEntry points, external skill dirs, local libs, text skills, Python skill files.
loadInstantiate, attach as self.<name>, call skill.attach(self), keep hidden by default.
activateResolve requires, unhide from doc(self), register dynamic context blocks, refresh slash commands.
class SkillRegistry(Skill):
    """Manages skill discovery, loading,
    and activation."""

    context_block = (
        "skills",
        "self.skills.status()",
    )

    def activate(self, patterns):
        self.load(not_loaded)
        self._resolve_deps(name)
        self._unhide_skill(name)
        self._register_context_block(name)
        refresh_skill_commands()

scale out.

09 GitLab CI · goal

Make CI and review
interrupt-driven.

The goal is not “call the GitLab API.” The goal is to babysit an MR until it is merged: surface failing jobs, reviewer comments, conflicts, new pipelines, recovery, and final merge/close — while staying quiet when nothing actionable happened.

  • The slash command does real work: parses the MR, creates the queue, and starts the monitor.
  • The agent does not set up plumbing: it just reacts when the monitor returns to the queue.
  • Notifications are semantic: “job failed”, “reviewer commented”, “conflicts detected”.
@slash_command("monitor", argument_hint="<mr>")
def monitor(self, mr_ref, *, auto_rebase=True):
    channel_name = f"mr-{iid}"
    qm.queue(channel_name, replace=True)
    qm.spawn(
        self.monitor_until_merged(project, iid),
        channel=channel_name,
        buffer=50,
    )
    # after this, the agent just waits/reacts
    return "👀 Monitoring !{iid}"

12 Agent Mesh · goal

Make agents
addressable peers.

Multi-agent systems need addressable peers: reviewer, fixer, release bot, benchmark bot. The mesh skill gives each one a durable handle, roster, direct messages, shared channels, and reconnection.

  • Identity: stored handle + ownership token survive restarts.
  • Topology: send to one agent or to #channels.
  • Reliability: reconnect and re-subscribe are skill behavior, not prompt instructions.

13 Agent Mesh · lifecycle

Lifecycle hooks carry
durable behavior.

On attach, the skill subscribes to session-resume and can auto-reconnect when stored credentials exist. On detach, it unsubscribes. This is the harness evolving: connection policy lives in code, not in every prompt.

attach(agent)Register TuiSessionResumed, store unsubscribe callback, trigger reconnect after hot reload/session restore.
connect()Resolve stored config, open client, create inbox channel, spawn inbox pump.
detach()Remove event subscription and let the Skill base detach from the agent.
def attach(self, agent):
    super().attach(agent)
    em = agent.event_manager
    em.register_event_type(TuiSessionResumed)
    self._unsub_resumed = em.on(
        "TuiSessionResumed",
        self._on_session_resumed,
    )

    if self.stored_name() and self.stored_token():
        self._on_session_resumed(None)

15 Session Search · goal

Make the harness
remember its own runs.

Session Search is the “framework is just Python” case study. It gives an agent memory over its own past traces: SQLite FTS over historical event logs and todos, returning structured objects it can navigate, cite, and export.

  • Find failures: search PythonOutput errors across sessions.
  • Recover context: jump from one event to the whole turn or call ID.
  • Package evidence: export a repro slice from the event DB.

19 Self evolution

The harness can
teach itself.

This is how the case-study Skills were built: the agent discovered missing capabilities, wrote or edited Skill libraries for itself, added tests, reloaded them, activated them, and kept working. The new behavior becomes part of self; the new status becomes part of context; the new commands become part of the UI — no system restart.

  • Reusable learning: save patterns as a Skill, not another prompt note.
  • Runtime upgrade: hot reload avoids stopping the session.
  • Prompt upgrade: activation changes what the model can see and call.
# discover a missing operation
await self.libs.create("trace_tools")

# edit ordinary Python files
await self.shell.replace(match, new_text)

# verify before believing
await self.shell.run("uv run pytest tests/trace_tools")

# load into the running harness
self.libs.reload("trace_tools")
self.skills.activate(["local.trace_tools"])
19a Takeaway for agent harnesses

Design the harness as
source + renderers.

Do not put everything in the prompt. Put durable facts in source-level abstractions the model already understands, then build narrow renderers that show the live state needed for the next action.

  • Source owns behavior: queues, hooks, clients, DBs, retries, tests.
  • Rendered context owns awareness: active jobs, pending items, available APIs, recent failures.
  • The agent can improve both: edit the source, then validate the rendered context changed.
