00 The premise

An agent is
a class.

An agent is a bundle of state and capabilities. We already have an abstraction for that — the object. Subclass Agent, and the runtime does the rest.

…

Ellipsis = agent loop. An ... body runs an agent loop. No ellipsis → an ordinary Python method.

"""…"""

Docstring = prompt. Describe the task; arguments arrive as live Python values.

sig

Signature = contract. Typed inputs and outputs are validated — type hints, Pydantic models, fields, and constraints.

class MyAgent(Agent, llm=llm):

    # deterministic — a tool the LLM may call
    def get_stock(self, item: str) -> int:
        return INVENTORY.get(item, 0)

    # generation — the LLM implements this
    async def analyze(self, data: str) -> Result:
        """Analyze the data. Use self.get_stock()
        for inventory checks."""

01 Strongly-typed methods

Agent loops
are methods.

The signature is the interface; the return type is a contract. Pydantic constrains the model response, validates the object, and retries on mismatch. Constraints like ge=0, le=1 are enforced, not hoped for.

02 Pass-by-reference

Inputs, outputs,
and arguments are variables,
not text.

The model gets a name, type, and one-line preview — then works on the real object. It can inspect the mesh, discover Plotly with doc(), and render the figure. Objects pass by reference; text is a deliberate rendering choice.

03 Code as action

Python is
the action.

No tool-call JSON. The model emits Python that runs in a REPL, sees the real stdout, and reasons over it next turn. And Python is expressive: conditionals, loops, comprehensions, method calls — compact, composable, and a language every 2026 model speaks fluently. One cell does what a dozen tool calls can't.

04 Loop engineering

Mix orchestration
and agent loops.

Plain methods and generation methods are both just methods, so you compose them with ordinary Python — for, while, if, asyncio.gather. Hand-written orchestration and agentic loops interleave freely in the same code. And the agent can write that orchestration too.

companion · 04_loop_engineering 
class Triage(Agent, llm=llm):

    async def severity(self, t: Ticket) -> int:
        """Rate ticket severity, 1–5."""
        ...

    async def run(self, tickets: list[Ticket]):
        # plain Python orchestrates the loop
        sev = await asyncio.gather(
            *(self.severity(t) for t in tickets))
        return [t for t, s in zip(tickets, sev) if s >= 4]
05 Object-based state

Store state on
the object.

An agent's state used to live entirely in the context window. Now it's also object state — ordinary fields on the instance. Here self.todo is a real manager on the object: the agent reads it, mutates it, and the next turn sees the new state. No external memory store; the instance is the memory.

06 Harness APIs

The harness
is an API.

The agent's own runtime is addressable. self.context shapes the system prompt as inspectable, mutable blocks; self.events is the trajectory. Both are first-class harness APIs — developers configure them at definition time, agents mutate them at runtime, through the same dict-like interface.

Each cycle re-renders the context — fresh dynamic tail, new events appended — and feeds it back, until the model calls return_result().

  • Generation is recursive. “run code” can call tools, create subagents, and await asyncio.gather(...) over generation methods — all standard Python.
  • Code and generation interleave. The ellipsis is simply where control crosses from your Python into the model and back.

Deep dive · what the LLM sees

The agent sees
Python I/O.

The agent is not just chatting with a user. It experiences the system — objects, context, tool results, stdout, and history — as Python-shaped input and output. One renderer keeps that world coherent.

  • doc(self) — signatures, types, docstrings
  • pprint() — values & objects, smartly truncated
  • code output — stdout + the return value
  • context & events — XML blocks & the trajectory
07 The context window

Three zones, ordered
for prompt caching.

Everything the model sees is assembled into one window. The order isn't cosmetic — the volatile part is pushed to the very end so the stable bytes in front of it stay byte-identical across turns and the provider's prompt cache can hit.

  </project_state>

08 Dynamic blocks

Dynamic blocks
are code.

The second argument to set_dynamic() is any Python expression, as a string — a method call, an f-string, a comprehension, attribute access. The runtime re-evaluates it at render time on every turn, so the prompt always reflects current state. Static is the counterpart: self.context["k"] = v is computed once and frozen into the cacheable prefix.

Turn by turn

The window is
rebuilt every turn.

Render the context, the model writes code, its PythonOutput lands as an event — then the next render folds it in. The static prefix stays byte-identical (a cache hit) while the event log grows and the dynamic tail recomputes from live state. Watch it run. →

What we've

Notes from building — and running — these agents.

What we've learned · 01

LLMs from 2026
just get it.

Today's models reason fluently about classes, async, and ordinary Python idioms — so the "mid-distribution Python" bet paid off. Minimal scaffolding; the model fills in the rest. The abstraction we didn't invent is the one it already knows.

What we've learned · 02

Don't make one
method switch modes.

Ask a single method to both classify and write code and it does neither well — a sentiment label buried in a code-acting method becomes a shitty classifier. One method, one task: PredictStrategy to classify, CodeAct to act.

# ✗ classification tangled into a code-acting method
@strategy(CodeActStrategy())
async def triage(self, text: str) -> Label:
    """Classify sentiment, then file a ticket."""  # confused
    ...

# ✓ split — one task each, the right strategy each
@strategy(PredictStrategy())
async def sentiment(self, text: str) -> Label:
    """positive / negative / neutral""" ...

async def triage(self, text: str) -> Ticket:
    """File a ticket using self.sentiment().""" ...
What we've learned · 04

We love & hate
Python.

It's the right substrate — the model knows it, it's expressive, control flow is free. But it fights back. This is the gap a purpose-built language for agents would close.

▍ what we love

  • The model already speaks it — no new syntax to teach.
  • Expressive control flow — loops, recursion, helpers, all free.
  • Objects as agents — state, tools, and identity in one place.

▍ what fights us

  • Concurrency seams — sync, async, and threads meet at every boundary.
  • Sandboxing is hard — arbitrary code needs real isolation and policy.
  • Serialization fights back — state and objects do not cross process boundaries cleanly.
  • Library docs are uneven — agents need structured docs, but Python has no standard.
