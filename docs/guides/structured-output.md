# Enforcing Structured Output

## Return Types as Contracts

When a generation method has a Pydantic `BaseModel` as its return type, the runtime forces the LLM to produce output matching that schema. This is the primary mechanism for getting reliable, structured results from LLM-powered methods.

```python
class Intent(BaseModel):
    task_type: Literal["question", "feature", "bugfix", "refactor"]
    summary: str

@strategy(PredictStrategy())
async def classify_intent(self, msg: str) -> Intent:
    """Classify {msg} into a task type."""
    ...
```

The LLM must return valid JSON matching `Intent`. If it doesn't, the strategy retries.

## Validating LLM-Generated Code with Pydantic

A pattern proven in the DABStep agent (see `experiments/evaluation-ablations/agents/dabstep_agent008.py`): use Pydantic's `@field_validator` to AST-validate code the LLM generates, ensuring it compiles before being accepted.

```python
import ast

class PythonSource(BaseModel):
    """Validated Python source code."""
    code: str = Field(description="Python source code")

    @field_validator("code")
    @classmethod
    def validate_python_syntax(cls, v: str) -> str:
        """Validate that code is syntactically valid Python."""
        if not v.strip():
            return v
        try:
            ast.parse(v)
        except SyntaxError as e:
            raise ValueError(f"Invalid Python syntax: {e}") from e
        return v

class ComputedAnswer(BaseModel):
    answer: Any = Field(description="The answer value")
    explanation: str = Field(description="How it was computed")
    source_code: PythonSource | None = Field(
        default=None,
        description="Python code used to compute the answer",
    )
```

**Why this works**: When the LLM returns a `ComputedAnswer`, Pydantic validates the `source_code` field with `ast.parse()`. If the generated code has syntax errors, the validation fails, and the strategy retries with the error message — giving the LLM a chance to fix its code.

## When to Use Validated Return Types

| Situation | Return Type Approach |
|-----------|---------------------|
| Simple classification | `BaseModel` with `Literal` fields |
| Structured data extraction | `BaseModel` with typed fields |
| LLM generates code | `BaseModel` with `@field_validator` + `ast.parse()` |
| Free-form response | `str` or `None` (no structured output) |
| Multi-field with constraints | `BaseModel` with `@field_validator` for custom checks |

**Avoid raw `dict` or `list` as return types.** Use a typed `BaseModel` instead — it gives the LLM a concrete schema to target, enforces the contract at validation time, and makes your code self-documenting.

## Pre-Implemented Helpers vs LLM-Generated Code

A lesson from DABStep optimization (63 iterations, 40% to 80% accuracy):

**Pre-implemented helper functions in code beat prompts every time.**

When you leave logic to the LLM, it gets it wrong inconsistently. When you provide deterministic helper functions, accuracy jumps.

```python
# BAD: Leave fee matching to the LLM
@strategy(CodeActStrategy())
async def compute_fee(self, transaction: dict) -> float:
    """Compute the fee for this transaction using the fee rules."""
    ...

# GOOD: Provide deterministic helpers, let LLM orchestrate
class MyAgent(Agent, llm=llm):
    def fee_matches(self, fee: dict, txn: dict) -> bool:
        """Deterministic fee matching — not generated by LLM."""
        if fee['card_scheme'] != txn['card_scheme']:
            return False
        if fee.get('is_credit') is not None:
            if fee['is_credit'] != txn['is_credit']:
                return False
        return True

    @strategy(CodeActStrategy())
    async def compute_fee(self, transaction: dict) -> float:
        """Compute the fee for {transaction}.
        Use self.fee_matches() to find matching fees.
        Use self.calc_fee() to compute the amount."""
        ...
```

Helpers are visible via `doc(self)`, so the LLM knows they exist and how to call them.

### When to Use Helpers vs LLM Generation

| Logic Type | Approach |
|-----------|----------|
| Domain rules with exact semantics | Pre-implemented helper |
| Fuzzy matching, interpretation | LLM generation |
| Data transformation with known schema | Pre-implemented helper |
| Multi-step reasoning | LLM with CodeAct |
| String formatting, parsing | Pre-implemented helper |

## Verification and Quality Gates

Another lesson from DABStep: **evidence before assertions.**

Before any agent claims work is complete, it must run verification:

```python
async def respond(self, msg: str):
    # ... do the work ...

    # Verification gate — pure Python enforcement
    evidence = await self.verify()
    if not evidence.tests_pass:
        await self.fix_failures(evidence)
        evidence = await self.verify()  # Re-verify

    # Only now report success
    await self.report_completion(evidence)
```

The verification step is NOT optional. The orchestrator (pure Python) enforces it. The LLM cannot skip it.
